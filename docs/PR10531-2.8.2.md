# Experimental E22P / I2C alpha with duplicate MQTT uplinks

Base: official Meshtastic v2.8.2.d5f1619, commit d5f16191ca28b01b5024f590f04a67f25d66f1b1. The revoked 2.8.2.4c89b69 release is not used.

Credit: ianmcorvidae's [PR10531](https://github.com/meshtastic/firmware/pull/10531), reviewed at head 40ac9fb1099680f93411786e82f0a471de5e1555, introduced opt-in duplicate MQTT analytics. This repository carries an adaptation, not the original PR verbatim. Meshtastic contributors provide the underlying routing, authentication, MQTT and platform code. ascendr's cb718ee5 E22P recipe supplies D5 enable, gain8 and chip max22. Existing CREDITS.md and GPL license apply.

## Scope and departures from the PR

- A separate environment, spicy_e22p_i2c_pr10531, enables USERPREFS_MQTT_UPLINK_ALL_SEEN=1. E22P wiring and I2C6/7 remain the same.
- Only authenticated, successfully decoded duplicate or hop-upgrade packets reach the added helper. Existing ignore lists, pre-hop filtering and ingress authentication run first.
- The helper decodes a pool-owned copy and retains the received wire image. It does not mutate the routing input, call modules, deliver messages to the phone, enqueue RF transmission or change routing history.
- Rejected, fatal, undecodable and unknown-channel results are not published by the added path. Existing decoded-content exclusions (pre-hop, disabled neighbor/beacon, core/event ports and blocked event coordinates) are also checked. MQTT::onSend retains its channel, precision, encryption and loop-prevention checks.
- Normal dispatchReceived() and opaque-PKI handling are left unchanged. Unlike the older PR, this port does not expand uplinking of opaque PKI or unknown-channel duplicates, or refactor normal received MQTT publishing. It keeps the newer alpha's separate opaque-DM dedup policy.
- Every accepted duplicate can add MQTT load and crypto work. For private broker analytics; it does not add RF retransmissions. On nRF52, MQTT needs a configured client proxy/bridge or supported network transport; the XIAO has no Wi-Fi. Receiving duplicates in a broker does not guarantee an analytics application retains them.

## Validation and use

The workflow compiles the actual added C++ helper in a host regression harness with mocked packet-pool and MQTT services. It covers successful publishing, unchanged input, all non-success decode states, both allocation failures, MQTT disabled/absent/loop input, empty packet ID, pre-hop/content restrictions and core-port filtering. It also checks that original normal-dispatch and opaque-PKI function text stays unchanged and authentication still precedes duplicate filtering. These are focused unit checks, not a complete live-radio or cryptographic integration test.

The nRF52840 build and UF2/OTA collector must pass before firmware artifacts are uploaded. The artifact includes the actual adapted patch, port script, host test and generated hardware variant as corresponding modification source. Existing 2.8.1 files and standard alpha are retained.

Use only on E22P hardware, not E22-900M33S 2W. Bench test against a standard-alpha baseline on a private MQTT broker. Confirm repeated (from,id) observations with distinct relay/SNR fields, and verify ignored/authentication-rejected/MQTT-originated traffic stays excluded. Check radio operation, sensors, memory and reboot/OTA recovery before deployment. The previous BLE verification timeout is unresolved; a successful compile does not establish mast-ready OTA reliability. No hardware is flashed by this workflow.

Use the experimental UF2 for USB, or its intact -ota.zip only if the Android updater accepts the connected device target. Its experimental target name intentionally differs from the standard E22P environment; do not rename unrelated binaries to bypass target checks. No factory erase is required for a normal application update, but back up configuration first. Review upstream XEdDSA/licensed-mode changes in the 2.8.2 release notes.
